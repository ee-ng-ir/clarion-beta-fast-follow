# IR prototypes

One repo for every IR product prototype and the shared consoles. Each app deploys as its own Vercel project.

## Folder setup

This repo is **not** inside any product's folder. The consoles serve every Iris product, so the repo sits beside the product folders:

```
IR Design/Projects/
├─ picasso/               Design system repo (source of @ir/ui). Synced into this repo.
├─ ir-prototypes/         ← this repo: all runnable prototypes
├─ Clarion/               Clarion's product folder: research, specs, brand assets, Figma exports
└─ <Next product>/        The next product's folder, same idea
```

**Rule of thumb:** code you run goes in `ir-prototypes`. Thinking, docs and assets about one product go in that product's folder.


How the apps relate:

| Layer | Apps | Serves |
| --- | --- | --- |
| Products | `clarion` (+ `clarion-widget`) | One product's users: CC managers, agents |
| Shared consoles | `client-console`, `ops-console` | Every product: customer IT admins, IR staff |
| Shared packages | `picasso`, `mock-data`, `telemetry` | Every app |

## Adding a new product

Say the next product is **Beacon**.

1. **Product folder.** Create `IR Design/Projects/Beacon/` for its docs, research and assets. No code there.
2. **Product app.** Add `apps/beacon/`. Copy `apps/ops-console` as a clean Picasso starter (or `apps/clarion` if it needs a dashboard shell). Then:
   - set `"name": "beacon"` in its `package.json`
   - give it the next free port in the `dev` script (5177, 5178…)
   - add `VITE_BEACON_URL` to `src/lib/apps.ts` in the apps that link to it
3. **End-user or companion apps** (an agent widget, a mobile view) go in `apps/beacon-<thing>/`, like `apps/clarion-widget`. If it must share live state with the product, serve it under the product's URL, the same way Clarion serves its widget at `/widget`.
4. **Access in the client console.** Add Beacon to `products` in `packages/mock-data/src/access.ts`. The **Tenant · Clarion · Beacon** tabs on Users, Groups and Roles appear automatically. Then write what Viewer, Editor and Product Admin mean in Beacon (the Beacon team agrees this mapping).
5. **Beacon's admin pages** (its equivalent of Clarion's Widget users) go in `apps/client-console`, as a **Beacon** section in the sidebar (`adminNavSections` in `src/nav.ts`). Not in the Beacon app.
6. **IR-internal Beacon tooling** goes in `apps/ops-console`.
7. **Data more than one app needs** goes in `packages/mock-data`, so the same tenant and people show up everywhere.
8. **Deploy.** Create a Vercel project with Root Directory `apps/beacon` and add the `VITE_*_URL` variables (see below).

Naming: app folders and package names are lower-case kebab (`beacon`, `beacon-widget`). Product names in copy are as branded (Clarion, never Clarity).

## Run it

```bash
npm install                    # once, at the repo root
npm run dev                    # every app
npm run dev:clarion            # Clarion + its widget (open /widget/ on the Clarion port)
npm run dev:console            # or: dev:ops, dev:clarion-widget
npm run build                  # builds everything (Turborepo caches unchanged apps)
```

Node 22 (see `.nvmrc`).

## Working on Picasso

Edit Picasso in `Projects/picasso`, not here. While `npm run dev` (or any `dev:*`) is running, it watches Picasso and copies changes into `packages/picasso`; the apps hot-reload. It watches `packages/ui/src` and the built token CSS (`packages/tokens/dist/tokens.css`, `themes.css`, `theme.css`), so after editing token JSON run Picasso's token build.

- **Deploys use the committed copy.** Vercel can't see your Picasso folder, so before you push: `npm run sync:picasso`, then commit `packages/picasso` (its `VERSION.json` records the Picasso commit).
- **No Picasso folder?** Dev says so and uses the committed copy.
- **Getting changes into IR's Picasso** is a Picasso-repo job: commit there and push to both remotes (`origin` on GitHub, `ir` on git.ir.local). This repo never pushes to Picasso.

## Deploying to Vercel

Create **one Vercel project per app** (not per package), all pointing at this repo:

| Vercel project | Root Directory |
| --- | --- |
| clarion | `apps/clarion` (also serves the Clarion widget at `/widget`) |
| client-console | `apps/client-console` |
| ops-console | `apps/ops-console` |

1. Vercel → Add New → Project → import this repo, then set the **Root Directory**.
2. Leave framework, install and build settings as they are. Each app's `vercel.json` handles them, and Vercel installs from the repo root because it's an npm workspace.
3. **Environment variables** (Production and Preview) in every project, so the apps can link to each other:
   - `VITE_CLARION_URL` = the clarion project's URL
   - `VITE_CLIENT_CONSOLE_URL` = the client-console project's URL
   - `VITE_OPS_CONSOLE_URL` = the ops-console project's URL
4. `"ignoreCommand": "npx turbo-ignore"` in each `vercel.json` means a push only rebuilds the apps it touched (or a package they use).

## Clarion widget → dashboard (live)

The Clarion widget is served **under the Clarion URL at `/widget`**. Clarion's build copies the widget build into `dist/widget`; in dev, Clarion proxies `/widget` to the widget's server. Same origin means they share a browser feed (`@ir/telemetry`: BroadcastChannel + localStorage). No backend.

1. Open Clarion (`/`) in one window and the widget (`/widget/#/demo`) in another, in the same browser.
2. In the widget's demo panel, pick an **agent** (Jordan · Sydney, Maria · Manila, Tom · London, Aisha · New York) and simulate an issue.
3. Clarion updates at once: that agent's endpoint, its location on the map, the KPIs, issues and alerts, plus a toast. **Open in Clarion ↗** jumps to the agent's machine.
4. **Reset all agents** puts the dashboard back to its generated data.

How each widget state shows in Clarion is one table: `packages/telemetry/src/mapping.ts`. Network loss, "reconnecting" and "not licensed" show the machine as **offline**, because it can't report.

## How the apps link

- Clarion's account menu → **Go to Admin Portal** opens the client console. Old `/admin/*` and `/setup/sso` links on Clarion redirect there.
- The client console's **Back to Clarion** opens Clarion.

## Where things go

| It's… | Goes in |
| --- | --- |
| A screen a product's users use day to day | `apps/<product>` |
| A product's companion app (agent widget, mobile) | `apps/<product>-<thing>` |
| Anything a customer's IT admin configures (access, SSO, a product's admin) | `apps/client-console` |
| Internal IR staff tooling | `apps/ops-console` |
| Data more than one app needs | `packages/mock-data` |
| Live state shared between a product and its companion | `packages/telemetry` (or a sibling package) |
| Design docs about one app | next to that app (e.g. `apps/client-console/RBAC-PROPOSAL.md`) |
| Research, specs, assets about one product | `IR Design/Projects/<Product>/` |
